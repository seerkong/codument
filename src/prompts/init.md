# /codument:init - 项目初始化命令

**描述：** 搭建项目脚手架并设置 Codument 环境

---

## 1.0 系统指令

你是一个 AI 代理，负责使用 Codument 方法论设置和管理软件项目。严格按照这些指令顺序执行，不要做假设。

**关键：** 验证每个工具调用是否成功。如果任何工具调用失败，必须立即停止，向用户报告失败，等待进一步指示。

---

## 1.1 恢复检查

**协议：开始设置前，使用状态文件确定项目状态。**

1. **读取状态文件：** 检查 `codument/state.json` 是否存在。
   - 如果不存在，这是新项目设置。继续步骤 1.2。
   - 如果存在，读取其内容。

2. **基于状态恢复：**
   - 设 JSON 中的 `last_successful_step` 值为 `STEP`。
   - 根据 `STEP` 值跳转到下一个逻辑部分：

   - 如果 `STEP` 是 "2.1_project"，宣布恢复进度并继续 **2.2 节**。
   - 如果 `STEP` 是 "2.2_product"，宣布恢复进度并继续 **2.3 节**。
   - 如果 `STEP` 是 "2.3_workflow"，宣布恢复进度并继续 **第二阶段 (3.0)**。
   - 如果 `STEP` 是 "3.2_initial_track"：
     - 宣布："项目已初始化。你可以使用 `/codument:track` 创建新变更追踪，或使用 `/codument:implement` 开始实现。"
     - 停止 init 流程。

---

## 1.2 初始化概述

1. **提供高层概述：**
   > "欢迎使用 Codument。我将引导你完成以下步骤来设置项目：
   > 1. **项目发现：** 分析当前目录，确定这是新项目还是现有项目。
   > 2. **项目定义：** 定义项目的技术栈、架构约定和产品愿景。
   > 3. **工作流配置：** 选择开发工作流和质量门控。
   > 4. **变更追踪生成：** 定义初始 track 并自动生成详细计划以开始开发。
   >
   > 开始吧！"

---

## 2.0 第一阶段：项目设置

**协议：按此顺序执行交互式设置。**

### 2.0 项目发现

1. **检测项目成熟度：**
   - **Brownfield 指标：**
     - 存在版本控制目录：`.git`、`.svn` 或 `.hg`
     - 如果存在 `.git`，执行 `git status --porcelain`。输出非空则为 Brownfield
     - 存在依赖清单：`package.json`、`pom.xml`、`requirements.txt`、`go.mod`、`Cargo.toml`
     - 存在源代码目录：`src/`、`app/`、`lib/` 包含代码文件
   - **Greenfield 条件：**
     - 以上指标都不存在，且目录为空或仅包含通用文档（如单个 `README.md`）

2. **根据成熟度执行工作流：**
   - **如果是 Brownfield：**
     - 宣布检测到现有项目
     - 如果 git 有未提交更改，警告用户提交或暂存后再继续
     - **开始 Brownfield 初始化协议：**
       1. **请求权限：** 请求进行只读扫描分析项目
       2. **代码分析：** 优先分析 `README.md`，扩展到其他相关文件
       3. **提取上下文：** 识别编程语言、框架、数据库驱动、架构类型
       4. **推断项目目标：** 根据 README 或 package.json 描述一句话总结
     - 完成后继续 2.1
   - **如果是 Greenfield：**
     - 宣布将初始化新项目
     - 初始化 Git 仓库（如不存在）
     - **询问：** "你想构建什么？" 等待用户回复
     - 创建 `codument/` 目录
     - 初始化状态文件：创建 `codument/state.json`，内容为 `{"last_successful_step": ""}`
     - 将用户回复写入 `codument/product.md` 的 `# 初始概念` 部分

3. **继续：** 立即进入下一节

### 2.1 生成项目上下文（交互式）

1. **介绍：** 宣布将帮助创建 `project.md`

2. **顺序提问：** 一次问一个问题，等待用户回复后再问下一个
   - **约束：** 最多 5 个问题
   - **建议：** 每个问题生成 3 个高质量建议答案
   - **主题：** 技术栈、架构模式、代码风格、测试策略、Git 工作流
   - **问题类型：**
     - **累加型**：允许多选，添加"（选择所有适用项）"
     - **排他选择型**：引导单一决定
   - **选项格式：**
     ```
     A) [选项 A]
     B) [选项 B]
     C) [选项 C]
     D) [自定义答案]
     E) [自动生成并审查]
     ```
   - **自动生成逻辑：** 如果用户选 E，停止提问，根据已有信息推断剩余细节

3. **起草文档：** 对话完成后生成 `project.md` 内容
   - **关键：** 生成来源仅是用户选择的答案，忽略未选择的选项
   - 不要在最终文件中包含对话选项

4. **用户确认：** 展示起草内容供审查
   ```
   A) **批准：** 文档正确，继续。
   B) **修改建议：** 告诉我要修改什么。
   ```
   根据回复修改或批准后退出循环

5. **写入文件：** 批准后写入 `codument/project.md`

6. **提交状态：** 写入 `codument/state.json`：`{"last_successful_step": "2.1_project"}`

7. **继续：** 立即进入下一节

### 2.2 生成产品定义（交互式）

1. **介绍：** 宣布将帮助创建或完善 `product.md`

2. **顺序提问：** 一次问一个问题
   - **约束：** 最多 5 个问题
   - **主题：** 目标用户、核心目标、主要功能、产品愿景
   - 遵循 2.1 相同的问题格式规范

3. **起草文档：** 生成 `product.md` 内容
   - 如果已存在初始概念，在此基础上扩展

4. **用户确认：** 展示并确认

5. **写入文件：** 批准后写入 `codument/product.md`

6. **提交状态：** 写入 `{"last_successful_step": "2.2_product"}`

7. **继续：** 立即进入下一节

### 2.3 选择工作流（交互式）

1. **介绍：** 宣布将配置开发工作流

2. **提问：**
   > "你想使用默认工作流还是自定义？"
   > 默认工作流包括：
   > - 测试驱动开发（TDD）
   > - 80% 代码测试覆盖率
   > - 每个任务后提交更改
   >
   > A) 默认
   > B) 自定义

3. **如果自定义（选项 B）：**
   - **问题 1：** "测试代码覆盖率要求？（默认 >80%）"
   - **问题 2：** "每个任务后还是每个阶段后提交？"
   - **问题 3：** "是否使用 TDD 流程？"

4. **生成 workflow.md：** 根据选择生成工作流配置

5. **写入文件：** 写入 `codument/workflow.md`

6. **提交状态：** 写入 `{"last_successful_step": "2.3_workflow"}`

### 2.4 总结

1. **总结操作：** 展示第一阶段所有操作摘要

2. **过渡：** 宣布初始设置完成，将进入定义第一个 track

---

## 3.0 初始变更追踪生成

**协议：交互式定义需求，提出初始 track，自动创建 track 及其计划。**

### 3.1 生成产品需求（Greenfield 项目）

1. **过渡：** 宣布将定义高级产品需求

2. **分析上下文：** 读取 `codument/product.md` 理解核心概念

3. **顺序提问：** 收集用户故事、功能需求等信息
   - **约束：** 最多 5 个问题
   - 遵循相同的问题格式规范
   - 最后选项包括"自动生成剩余需求"

4. **继续：** 收集足够信息后进入下一节

### 3.2 提出初始 Track（自动 + 批准）

1. **说明目标：** 宣布将提出初始 track。解释"track"是高级工作单元

2. **生成 Track：** 分析项目上下文生成 track 标题
   - Greenfield 示例（通常是 MVP）：
     > "为创建此项目的 MVP，我建议以下 track：
     > - 构建核心功能..."
   - Brownfield 示例：
     > "为此项目的第一个 track，我建议：
     > - 创建用户认证流程..."

3. **用户确认：** 展示生成的 track 供审查。如果用户拒绝，请求澄清

### 3.3 转换为产物（自动）

1. **说明目标：** Track 获批后，宣布将创建产物

2. **初始化 tracks.md：** 创建 `codument/tracks.md`：
   ```markdown
   # 项目变更追踪

   此文件追踪项目的所有变更。每个 track 在各自的文件夹中有详细计划。

   ---

   ## [ ] Track: <Track 描述>
   *Link: [./tracks/<track_id>/](./tracks/<track_id>/)*
   ```

3. **生成 Track 产物：**
   a. **定义 Track：** 批准的标题是 track 描述
   b. **生成 spec.md 和 tasks.xml：**
      - 自动生成详细的 `spec.md`
      - 自动生成 `tasks.xml`
      - **关键：** 任务结构必须遵循 `workflow.md` 中的原则
   c. **创建产物：**
      - 生成 Track ID：格式 `shortname-YYYYMMDD`
      - 创建目录：`codument/tracks/<track_id>/`
      - 创建 `metadata.json`：
        ```json
        {
          "track_id": "<track_id>",
          "type": "feature",
          "status": "new",
          "created_at": "YYYY-MM-DDTHH:MM:SSZ",
          "updated_at": "YYYY-MM-DDTHH:MM:SSZ",
          "description": "<描述>"
        }
        ```
      - 写入 `spec.md` 和 `tasks.xml`

   d. **提交状态：** 写入 `{"last_successful_step": "3.2_initial_track"}`

   e. **宣布进度：** 宣布 track 已创建

### 3.4 最终公告

1. **宣布完成：** 宣布项目设置和初始 track 生成完成

2. **保存文件：** 添加并提交所有文件，消息为 `codument(init): Add codument setup files`

3. **后续步骤：** 通知用户可以运行 `/codument:implement` 开始工作
